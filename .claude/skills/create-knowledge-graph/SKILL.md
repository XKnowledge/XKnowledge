# 创建 XKnowledge 知识图谱

为 XKnowledge（3D 力导向知识图谱软件）生成可直接打开的 `.xk` 图谱文件：节点 = 概念，
连接 = 关系，类目 = 颜色分组。`.xk` 是纯 JSON，但**能解析 ≠ 是好图谱**——本技能的
规范与校验脚本保证产出的图格式正确、内容结构值得打开看。

## 工作流

1. **确认主题与保存路径**。缺哪个问哪个，不要擅自决定。用户没想好主题时，可从
   `examples/候选知识图谱调研.md` 挑未实现的候选供参考。用户只给目录时，文件名用
   `主题名.xk`。
2. **先设计骨架，再动笔**（边想边写必出断图）：
   - 类目 5–9 个，每个类目是主题的一个自然切面（如"硬件体系 / 编程接口 / 生态工具"）；
   - 节点分三层：枢纽（每类目 1–2 个，`symbolSize` 60–70）→ 中坚（50）→ 叶子（30–40）；
   - 规模目标 60–120 节点（用户另有要求则从之），连接数约为节点数的 1.2–1.6 倍；
   - 动笔前先列出类目与各枢纽节点（一小段即可），直接开写容易结构失控。
3. **写文件**：以**一节点一行的可读 JSON** 写到目标路径，顶层字段序
   `version → nodes → links → title → description`。不要直接手写紧凑单行 JSON——
   长文件极易括号失配，紧凑化交给下一步。
4. **归一并校验（必须全绿才算完成）**：

   ```
   node <本技能目录>/scripts/validate-xk.mjs <file.xk> --fix
   ```

   `--fix` 把合法 JSON 归一为紧凑单行（与应用自身保存行为一致：无缩进、无尾换行、
   无 BOM），随后执行全部红线检查。出现 `✗ FAIL` 时修复后重跑。
5. **交付**：报告文件绝对路径 + 节点/连接/类目数 + 一句话内容概述。

## .xk v2 格式

UTF-8（无 BOM）JSON，紧凑单行存储（应用 `ChartView` 保存即无缩进 `JSON.stringify`）：

```json
{
  "version": 2,
  "nodes": [
    { "name": "莫高窟", "des": "敦煌鸣沙山东麓的石窟群，735 窟、4.5 万平方米壁画，丝路艺术的集大成者。", "symbolSize": 70, "category": "石窟与营建" },
    { "name": "藏经洞", "des": "第 17 窟，1900 年出土 5 万余件写本，直接催生了敦煌学。", "symbolSize": 50, "category": "石窟与营建" },
    { "name": "飞天", "des": "不长翅、不驾云、凭飘带凌空起舞的伎乐天，敦煌壁画的标志形象。", "symbolSize": 60, "category": "壁画艺术" }
  ],
  "links": [
    { "source": "莫高窟", "target": "藏经洞", "name": "包含", "des": "藏经洞即莫高窟第 17 窟。" },
    { "source": "莫高窟", "target": "飞天", "name": "标志形象", "des": "飞天是莫高窟壁画最具代表性的题材。" }
  ],
  "title": "敦煌石窟艺术",
  "description": "从凿窟营建到壁画彩塑，从藏经洞到敦煌学的千年艺术全景图。"
}
```

| 层 | 字段 | 约束 | 说明 |
| --- | --- | --- | --- |
| 顶层 | `version` | 固定 `2` | 缺失或不是 2，应用判损坏拒开 |
| 顶层 | `title` | 非空 | 图谱名，与文件名（去 `.xk`）一致 |
| 顶层 | `description` | 非空 | 一句话简介，首页卡片与属性面板"图谱简介"显示 |
| 节点 | `name` | 全图唯一主键 | 连接按它引用；应用按它作 nodeId |
| 节点 | `des` | 非空 | 一句书面说明，悬浮提示显示「名称：描述」 |
| 节点 | `symbolSize` | 1–100 | 球体大小，实际按立方参与渲染（70 与 50 视觉差明显） |
| 节点 | `category` | 非空 | 类目（着色分组），同名类目永远同色 |
| 连接 | `source` / `target` | 已存在的节点名 | 两端无方向 |
| 连接 | `name` | 非空 | 2–4 字关系词 |
| 连接 | `des` | 非空 | 一句话说明这对关系 |

## 内容设计规范

- **节点 des**：一句书面中文，带具体信息（年代、人物、机制、数字），不写空话。
  好例子见上方格式示例；「相关的重要概念」这类废话不如不写。
- **连接 name**：2–4 字关系词（隶属、组成、衍变、师承、对立、引发、标志形象……），
  `des` 补一句为什么连。
- **连通性**：3D 力导向图里断开的分量会各自飘成一簇，观感割裂——全库 207 例曾被
  专项修复成全连通（见 git log 2026-09-21）。设计时就让每个类目有 1–2 条跨类目边，
  用"桥知识"缝合（如用"丝绸之路"把"营建史"与"壁画题材"连起来）。
- **避免**：孤立节点、类目内密集互联而类目间零连接、只为凑数的中转节点。

## 红线清单（校验脚本逐条检查）

| # | 检查 | 为什么是红线 |
| --- | --- | --- |
| 1 | JSON 可解析、UTF-8 无 BOM、`version === 2`、`nodes`/`links` 为数组 | 任一不满足，应用判损坏拒开 |
| 2 | 连接 `source`/`target` 引用已存在节点（无悬空边） | 判损坏拒开 |
| 3 | 节点 `name` 全图唯一 | name 是主键，重名导致渲染与编辑错乱 |
| 4 | 无自环（source === target） | 无效关系 |
| 5 | 同两节点间仅一条连接（无向判定） | 应用创建连接时明令禁止重复 |
| 6 | 无孤立节点，全图单连通分量 | 力导向图断成几簇，观感割裂 |
| 7 | `symbolSize` ∈ [1, 100] | 应用表单硬限制 |
| 8 | 节点/连接各四字段与顶层 `title`/`description` 齐全且非空 | 全库 207 例统一约定；缺 description 时首页卡片简介为空 |

脚本另有 WARN 级提醒（节点数 < 20 或 > 300、类目 > 12、连接/节点比失衡、超长名称/
描述）。WARN 不阻塞交付，但应逐条斟酌后在交付说明里回应。修改既有 `.xk` 后同样
可用本脚本复核。

## 常见错误

| 错误 | 纠法 |
| --- | --- |
| 直接手写紧凑单行 JSON | 几百个对象挤一行，括号失配概率极高。先写一节点一行的可读 JSON，`--fix` 归一 |
| 连接引用了"计划里"但没写下的节点 | 写连接时只引用已写下的 name；脚本兜底拦悬空 |
| 两个节点同名（时代与风格都叫"古典主义"） | 用更具体的名字区分（"古典主义时期" / "古典主义美学"） |
| 类目间零连接导致多连通分量 | 每个类目预留跨类目边，用桥知识缝合 |
| 忘写 `title` / `description` | description 一句话回答"这张图讲什么、覆盖到哪" |
| 以 pretty 多行格式交付 | 能打开，但与应用保存行为及全库主流格式不一致。`--fix` 归一 |
